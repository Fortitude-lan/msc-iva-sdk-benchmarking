# RQ2 Protocol-Autonomy Spectrum Trade-offs (Conditions A / B / C)

**How this feeds RQ0:** doppelgänger research is not one paradigm, psychology-style studies need full scripted control, SEAM-style studies need constrained-but-autonomous agents, and exploratory HCI studies want to see what the AI does unprompted. RQ2 asks whether the same SDK can support all three without the researcher fighting the tool. A SDK that only serves one end of the spectrum is only "suitable" for a narrow slice of doppelgänger research — that's the finding RQ2 contributes back to RQ0, distinct from RQ1's "does the feature exist" question.


**Important framing:** these three conditions are not being ranked against each other to find a "best" mode. Each is the correct choice for a different kind of study; RQ2 documents what each one costs the researcher, so a future doppelgänger researcher can pick the right condition for their paradigm with eyes open.


## 1. The three conditions — overview

| Condition | Maps to research paradigm | Control mechanism | Feasibility |
|---|---|---|---|
| **A: Wizard-of-Oz** | Psychology-style scripted experiments | Human operator manually triggers `agent.Speak()` / `agent.PerformAction()` / `agent.ExpressEmotion()` via a custom UI | Feasible, but **not natively supported** — requires building a ~200-line operator panel |
| **B: Constrained AI** | SEAM-style bounded autonomous agents | AI-driven via `GeminiLiveAgent`, constrained through the `additionalDescription` system-prompt field | Feasible — edit only, no custom UI needed |
| **C: Fully autonomous AI** | Exploratory / open-ended HCI research | SDK's existing `GeminiLiveAgent` sample, unmodified | Already exists — zero additional setup |

---
### Condition A - Wizard-of-Oz
#### What gets built
A minimal Unity UI panel with preset buttons, each calling one public API method directly:

- Buttons for 3–5 scripted lines → `agent.Speak(text)`
- Buttons for 2–3 gestures → `agent.PerformAction(actionName)`
- Buttons for 2–3 expressions → `agent.ExpressEmotion(emotionName)`

---
*Note1: This condition establishes a baseline for the fully human-controlled end of the autonomy spectrum. It produces comparable data for setup effort, latency, control precision, predictability, and reproducibility, which can later be contrasted with the constrained-AI and fully AI-driven conditions.*

*Note2: It also indirectly tests SDK extensibility: because the SDK does not provide a built-in operator-control panel, implementing a minimal control UI helps evaluate whether the SDK can be adapted for custom research workflows without modifying the SDK itself.*

---
### Condition B - Constrained AI
#### What gets built
Edit the `additionalDescription` field passed into GeminiLiveAgent.`BuildSystemPrompt()`. 
**Create a constraint text, like skill prompt**

---
*Note: For constrained-autonomy doppelgänger studies, the key question is whether the SDK provides enough engineering mechanisms to make the constraints enforceable, or whether it only exposes a bare LLM interface where the researcher writes the rules into the prompt and then relies on the model to follow them.*

---


### Condition C - Fully Autonomous AI

#### What gets built
Nothing additional — this condition uses the SDK's existing `GeminiLiveAgent` sample, unmodified. Confirmed via SDK inspection to require zero scoping-down; it is technically the simplest of the three conditions, despite representing the most autonomous end of the spectrum.

#### Task protocol
- Same fixed trigger question as Condition A/B, asked 10 times
- Timestamp trigger → response start for latency (directly comparable to B)
- Predictability: before each trial, note expected response content; after, score 0/1/2 against what was actually said
- Reproducibility: for repeated identical inputs, code whether core content (e.g. stated identity/role) stays consistent across trials
- No constraint set → constraint violation rate not applicable to this condition

---
*Note: Although this condition requires no build effort, it is not "untested" — it is the counterpoint needed to show that the autonomy spectrum's lowest-setup-cost end also carries the lowest predictability/reproducibility, which is the trade-off RQ2 needs evidence for.*

---

## 2. Evaluation metrics and definitions

**RQ2 examines the following claim:** the SDK’s suitability for doppelgänger research depends on the selected level of autonomy, because each autonomy condition creates different trade-offs for the researcher.

The evaluation metrics therefore represent the main practical concerns a researcher would consider when choosing between Conditions A, B, and C:

| Researcher consideration                                    | Metric                                             | Definition                                                                                       |
| ----------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| How much work is required to implement the condition?       | **Setup effort**                                   | Time, code, and external dependencies required to get the condition running from a clean project |
| Is the agent responsive enough for real-time interaction?   | **Behaviour latency**                              | Time between an input or trigger and the corresponding observable agent behaviour                |
| Can the researcher anticipate what the agent will do?       | **Predictability**                                 | Whether the researcher can anticipate the doppelgänger’s behaviour before it happens             |
| Will repeated trials produce comparable behaviour?          | **Reproducibility**                                | Whether the same setup and input produce the same behaviour across repeated trials               |
| Does the agent follow explicitly defined behavioural rules? | **Constraint violation rate** *(Condition B only)* | Proportion of elicitation trials in which the agent violates a stated hard constraint            |


### 3. Expected comparison across conditions

| Dimension | A (WoZ) | B (Constrained AI) | C (Fully AI) |
|---|---|---|---|
| Setup effort | Custom WoZ UI + TTS account | Prompt engineering | None (existing sample) |
| Control precision | High | Medium (unreliable — see 4.2) | Low |
| Flexibility | Low | Medium | High |
| Predictability | High | Medium | Low |
| Reproducibility | High | Medium (constraint violations add noise) | Low |
| Latency (execution only, same hardware) | Low–Medium | Medium | Medium–High |
| Risk of unwanted decision | Low | Medium-low (measured violation rate) | High |
| Research suitability | Controlled study | Semi-controlled study | Exploratory study |

---


*Note: These ratings are provisional expectations used to guide the evaluation design. After data collection, they will be compared with the measured results and replaced or revised in the final dissertation.*
