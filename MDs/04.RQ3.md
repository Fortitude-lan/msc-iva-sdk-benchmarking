## RQ3 Protocol — Developer Experience (Dev Journal + Usage Study)

**How this feeds RQ0:** RQ0 asks whether the SDK is suitable as a research platform — suitability isn't just "can it do the thing" (RQ1) or "what trade-offs come with each mode" (RQ2), it's also "can a researcher realistically pick this up and build with it." A platform that's feature-complete but practically unusable is not a suitable research platform. RQ3 is entirely how checklist category C9 (Developer Experience) in RQ1 gets its evidence.

## 1. Two evidence sources

| Source | What it covers | Where |
|---|---|---|
| 1. Researcher's own dev journal (self-as-developer) | Full build experience across Conditions A/B/C — especially C9.5 (Extensibility), via the WoZ-UI-building experience in RQ2 §2 | Ongoing, throughout RQ2 build work |
| 2. Independent usage study, 3–4 students | First-use experience on a stranger — controls for the researcher's own familiarity bias | This document, §2 onward |


## 2. Usage study — participants
 
- **3–4 fellow MSc/CS students**, general Unity/C# familiarity, **no prior exposure to this SDK** (prior exposure would bias the setup-effort measurement).
- External participants preferred over internal-lab participants where feasible, but not mandatory if well-argued — the priority is "no prior SDK exposure," not institutional distance.

## 3. Environment setup (prepared by researcher before each session — not part of the 15-minute task)
 
- New, clean Unity project, SDK and its automatically-installed dependencies already added via Package Manager
- Scene left empty — **no Agent GameObject pre-built**; participant builds this from scratch using only the SDK's documentation
- Gemini API key and TTS (ElevenLabs) key pre-filled in `auth.json` — participants are not asked to register their own third-party accounts, since this is unrelated to the SDK's own documentation quality
- Task sheet (Section 4) prepared as a printed/shared doc — not explained verbally beyond it
- Observation log template ready (Section 5)
- Consent script ready (Section 6)
---




## 7. Post-task questions (5–7 min)
 
1. On a scale of 1–5, how clear was the documentation for this task? *(1 = very unclear, 5 = very clear)*
2. On a scale of 1–5, how much effort did this task take compared to what you expected? *(1 = much more than expected, 5 = much less)*
3. What was the single most confusing part?
4. Was there a moment you weren't sure what to do next? What did you try?
5. If you had to explain this SDK's speech-triggering mechanism to another student in one sentence, what would you say? *(tests whether the mental model formed correctly)*
6. *(Optional, cross-validates Section 8)* Did you notice the README's reference to the Wiki? If you followed it, what was that experience like?
---

## 8. Session timeline (30 min total)
 
| Time | Phase | What happens |
|---|---|---|
| 0–3 min | Intro + consent | Explain purpose (evaluating an SDK, not the participant), confirm consent, explain think-aloud |
| 3–20 min | Task (think-aloud, ~15–17 min with buffer) | Participant attempts the task using only SDK docs |
| 20–27 min | Post-task questions | Structured questions above |
| 27–30 min | Wrap-up | Thank participant, answer questions, stop recording |
