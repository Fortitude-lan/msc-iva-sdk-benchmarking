# RQ1 What doppelgänger-relevant capabilities does the SDK support, and where are its practical boundaries?


### What "practical boundaries" means

RQ1's checklist answers one thing per item: **whether a capability exists,
how directly it can be accessed/configured, and what SDK-level limitations
or workarounds apply.** This is deliberately narrower than "does it work
reliably" or "can a real developer actually use it" — those are empirical
questions answered separately, by RQ3 (constraint reliability) and RQ4
(developer experience) respectively, using their own evaluation methods
(technical performance / usage evaluation, per Ledo et al.). Capability
existence alone does not establish behavioural reliability or developer
usability.


---
Every scored item records: **Evidence type** (`code` / `doc` / `test`), **1-line justification**, **API/file reference**.

## C1 — Avatar Representation (2 items)
 
**Why this category is here:** Embodied visual representation is listed as a defining capability of an IVA toolkit by its own authors (Li et al., 2026). For doppelgänger research specifically, the stand-in is explicitly defined as "an embodied virtual agent" representing the absentee (Bai et al., 2025) — so how flexibly that embodiment (appearance, voice) can be configured is not a cosmetic detail but core to whether attendees perceive the agent as an adequate stand-in.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C1.1 | Avatar import/swap (realistic or stylised) | Open the SDK's avatar setup docs/prefabs. Try assigning a different avatar prefab (e.g. swap in a Ready Player Me or similar model) to an existing Agent Base Class instance. Record: is this a drag-and-drop Inspector field, a documented API call, or does it require touching multiple scripts/scene objects? | 2 = single Inspector field/public method; 1 = works but needs manual scene rewiring across multiple components; 0 = not documented/not reachable | Li et al., 2026 — avatar customization is listed as a core toolkit capability |
| C1.2 | Custom/cloned voice for the agent | Check TTS service config (ElevenLabs/Azure/Google Cloud) for a voice-selection or voice-cloning parameter. Attempt to set a specific voice ID. | 2 = voice ID settable via public field/param; 1 = possible only by manually editing cloud-service call code; 0 = not supported by integrated TTS providers | Bai et al., 2025 — SEAM's stand-in is designed to "mimic the absentee's communication style," which includes voice identity |

## C2 — Speech / Verbal Behaviour (3 items)
 
**Why this category is here:** Speech is listed among the toolkit's core multimodal capabilities by its own authors (Li et al., 2026). More specifically for doppelgängers, the stand-in exists precisely to "generate reasonable responses in meetings and mimic the absentee's communication style" via an LLM-driven voice channel (Bai et al., 2025) — so verbal behaviour control isn't optional, it's the mechanism the whole doppelgänger concept runs on.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C2.1 | Manual/scripted speech trigger, independent of LLM loop | Call `agent.Speak(text)` directly from a test script (not through the LLM pipeline) with an arbitrary string. Confirm the agent speaks exactly that text. | 2 = works directly, arbitrary text; 1 = works but only with pre-registered/whitelisted strings; 0 = not callable outside LLM loop | Needed specifically for WoZ-style / human-controlled doppelgänger studies — this is the primitive RQ2's human-controlled extreme relies on (Bai et al., 2025 discusses SEAM's own reliance on scripted/controlled responses in Study 1) |
| C2.2 | Multilingual STT/TTS support | Check docs/code for language parameter on STT and TTS services. Run one non-English utterance through STT if feasible, or confirm via documentation + config field. | 2 = language selectable via config, confirmed working; 1 = documented but not verifiable without extra account setup; 0 = English-only | General research-platform generalisability — not tied to a specific paper; included because a platform limited to one language restricts which participant populations doppelgänger studies can recruit |
| C2.3 | Interrupt / barge-in mid-speech | While the agent is mid-`Speak()`, call `agent.Speak()` again or a stop/interrupt method. Observe whether the first utterance is cut off cleanly or causes an error/overlap. | 2 = clean interrupt via public method; 1 = interrupt possible but causes audio overlap/glitch; 0 = no interrupt path found | Li et al., 2026 — the SDK's own end-user pilot evaluation found "multiple participants reported difficulties interrupting the IVA during long responses," i.e. this is a documented real limitation, not a hypothetical concern |

*Qualitative observation, not a scored item: hallucination/fabrication risk
in generated speech. This is a known LLM limitation, not an SDK feature gap,
so it is not assigned an ID or a 0/1/2 score. If RQ3's persona-constraint
testing or RQ2's AI-driven demonstration surfaces an instance where the
agent stated a fact about the represented person that was not in the
prompt/persona description, it is logged here as present/absent + example
(Bai et al., 2025 — SEAM explicitly names this risk: LLMs "lack access to
full contextual understanding... which can lead" to inaccurate stand-in
responses).*

## C3 — Non-verbal Behaviour (3 items)
 
**Why this category is here:** Gesture, facial expression, and gaze are explicitly listed among the toolkit's core multimodal capabilities (Li et al., 2026). More concretely, SEAM's own recording/replay mechanism depends on capturing "every movement (including gestures, facial expressions, locomotion...)" (Bai et al., 2025) — meaning non-verbal channels aren't decorative, they're part of what a stand-in must be able to reproduce for a doppelgänger experience to feel complete.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C3.1 | Manual/scripted gesture trigger | Call `agent.PerformAction(actionName)` directly for 3 different pre-built actions. Confirm each plays the correct animation on demand. | 2 = arbitrary registered action playable on demand; 1 = only reachable via LLM decision, not directly callable; 0 = not found | Li et al., 2026 — gesture control listed as core capability; needed as one of the manual-trigger primitives RQ2's human-controlled extreme draws on |
| C3.2 | Manual/scripted facial expression trigger | Call `agent.ExpressEmotion(emotionName)` directly for 3 different expressions. Confirm each renders correctly. | 2 = directly callable; 1 = only LLM-selected; 0 = not found | Li et al., 2026 — facial expression control listed as core capability |
| C3.3 | Gesture/expression library breadth relevant to doppelgänger use (culturally-adaptive, persona-consistent options) | Count distinct actions/expressions available in the shipped library (Action Manager / Facial Expression Manager asset lists). Check whether persona attributes (e.g. culture, personality) influence which actions the LLM selects. | 2 = large library (>20 actions) with documented persona-conditioned selection; 1 = library exists but persona-conditioning undocumented/untested; 0 = minimal library, no conditioning | Bai et al., 2025 — SEAM's ethics discussion raises whether "generated gestures or responses" are attributable to the system or the absentee, implying gesture selection needs to be persona-consistent, not generic |

## C4 — Listening / Input (2 items)
 
**Why this category is here:** The toolkit's own paper lists STT and "vision-based multimodal prompting" as core input capabilities (Li et al., 2026). More specifically, SEAM's stand-in is explicitly described as being "configured with their responses to the agenda items" ahead of time (Bai et al., 2025) — i.e. a doppelgänger needs to be primed with context beyond whatever it can pick up live through a microphone, which directly motivates C4.1.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C4.1 | External context injection bypassing live STT (e.g. feeding meeting transcript text directly) | Check for a public method/field that accepts text input directly (not through microphone/STT). Attempt to feed a test string and confirm the agent responds to it as if it had "heard" it. | 2 = documented text-injection API; 1 = possible only by spoofing STT output internally; 0 = no path found | Bai et al., 2025 — stand-ins are pre-configured with the absentee's responses/context, not purely reliant on live listening |
| C4.2 | Multimodal/visual perception of the environment or other participants | Check for VLM/vision input hooks. Test whether the agent can react to a simple visual cue (e.g. an object or avatar appearance) if hardware allows, or confirm via code walkthrough if hardware testing isn't feasible in the time available. | 2 = confirmed working visual input path; 1 = documented/code-present but not independently verified; 0 = not present | Li et al., 2026 — vision-based multimodal prompting listed as a core toolkit capability |

## C5 — Control and Autonomy (3 items)

**Why this category is here:** This is the category with the strongest, most direct literature grounding. SEAM's own ethics/trust discussion states the core tension this category operationalizes almost word-for-word: *"the extent to which stand-ins should respect absentee autonomy is unclear... without any control from the absentee, stand-ins may cause unexpected consequences"* and that *"providing transparent control systems is a crucial first step towards allowing absentees to trust their stand-in"* (Bai et al., 2025). C5 turns this literature-level statement into testable capability items: whether native operator tooling exists (C5.1) — manual-control existence itself is established by C2.1/C3.1/C3.2 — whether identity, role, context, and behavioural instructions can be configured (C5.2), and whether behavioural instructions receive any enforcement beyond raw prompt text (C5.3). On the WoZ-specific item (C5.1), Simpson et al. (2022) and the Welicit paper add a second, methods-level layer of grounding: both are studies whose entire contribution is building custom WoZ tooling for virtual environments precisely because none exists natively — confirming that this SDK's gap here is a known, documented pattern in the field, not an isolated flaw.

*The empirical reliability of the constraint mechanism identified in C5.3 —
whether it actually holds up under adversarial pressure — is evaluated
separately in RQ3, not scored here. RQ1 establishes what exists and how it
is architected; RQ3 establishes whether it works.*

| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C5.1 | Native WoZ/operator interface shipped with SDK | Doc/code search for any built-in operator panel or manual-override UI. | 2 = shipped and usable as-is; 1 = partial scaffolding exists but incomplete; 0 = none — confirmed absent, must build from scratch | Simpson et al., 2022 and the Welicit paper — both are entirely about researchers having to build custom WoZ tooling because none existed for their VR/virtual-environment context; this SDK's lack of native WoZ tooling is consistent with a documented gap in the field, not a unique shortcoming |
| C5.2 | Persona/role/behavioural-instruction configuration | Confirm `additionalDescription` field (or equivalent) accepts free-text input and is passed into `BuildSystemPrompt()`. This single field is what RQ2's AI-driven demonstration populates with identity/role/context, and what RQ3 populates with behavioural instructions (hard rules) — the same field, two different kinds of content, not two separate mechanisms. C5.3 then checks whether content of the second kind (behavioural instructions) receives any enforcement beyond being placed in the prompt. | 2 = confirmed field exists and is passed to system prompt; 1 = only settable by editing source; 0 = not present | Bai et al., 2025 — absentees need a way to prime the stand-in with identity/role/context and to bound what it can say/do. Also Li et al., 2026 — the SDK's own paper describes its high-level decision loop as combining user input with "a role prompt describing the agent's persona, available actions, facial expressions, and gaze behaviors" — i.e. "persona" is the SDK's own architectural term for this mechanism, not a label imported from outside |
| C5.3 | Enforcement mechanism beyond raw prompt-text injection | **Static code inspection, not an empirical trial.** Check `BuildSystemPrompt()` and the surrounding pipeline: once a behavioural instruction is placed into the field checked in C5.2, does the SDK do anything further to enforce it (validate output against the rule, reject/retry on violation, restrict output to a fixed schema/vocabulary), or does the text get concatenated into the prompt with no additional engineering safeguard? | 2 = explicit enforcement/validation layer confirmed (e.g. output checked, auto-retry on violation); 1 = partial safeguard (e.g. gestures/emotions are constrained to a fixed vocabulary, but free-text speech is unchecked); 0 = confirmed no enforcement layer — compliance rests entirely on the underlying LLM's own instruction-following | Direct source-code finding: `AgentBase.BuildSystemPrompt()` only concatenates `additionalDescription` into the prompt string; no validation/retry layer exists. This is the static, architectural finding that motivates RQ3's empirical question: given no enforcement layer exists in code, does the instruction hold up in practice anyway, purely on the LLM's own instruction-following? |

## C6 — Reproducibility / Logging (3 items)
 
**Why this category is here:** This is the second most directly-grounded category. SEAM's entire second-iteration mechanic depends on recording "every movement... voice and every object's changes in 3D space" so the absentee can later replay and review what their stand-in did (Bai et al., 2025) — this is a concrete, literature-stated functional requirement of doppelgänger systems, not just general good research practice.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C6.1 | Interaction logging (conversation history, actions taken) exposed programmatically | Code/doc search for a logging hook or accessible history object. Attempt to read back a log of the last N turns. | 2 = structured log accessible via public API; 1 = raw data exists but requires manual extraction/parsing; 0 = not exposed | Bai et al., 2025 — absentees need to be able to review "what the stand-in responded to during the meeting" |
| C6.2 | Deterministic manual trigger (same call → same output, non-LLM-dependent factors only) | Code-level check, no repeated trials: confirm that `agent.Speak()` / `agent.PerformAction()` / `agent.ExpressEmotion()` are direct method calls with no intervening non-deterministic step (e.g. no LLM call in between the invocation and the resulting behaviour). This is distinct from C2.1/C3.1/C3.2, which only establish that a direct call path *exists* — C6.2 checks whether that path is actually free of non-deterministic components (e.g. TTS voice rendering). This is the concrete evidence behind RQ2's human-controlled extreme claim that predictability/reproducibility are "maximal by construction" — that claim is otherwise just an assumption. | 2 = confirmed direct call path, no non-deterministic step involved; 1 = mostly direct, but one component (e.g. TTS voice rendering) introduces minor non-determinism; 0 = manual triggers still route through a non-deterministic step | Ledo et al., 2018 — general scientific-reproducibility expectation for a research platform, not doppelgänger-specific |
| C6.3 | Session/interaction recording (video/audio/state capture) | Doc/code search for a built-in session recorder. | 2 = built-in recorder available; 1 = requires external tool (e.g. screen recording) with no SDK-level state capture; 0 = no support, not even partial | Bai et al., 2025 — session recording is the literal mechanism SEAM's asynchronous replay is built on |

## C7 — Technical and Runtime Support (3 items)
 
**Why this category is here:** Ledo et al. identify technical performance reporting as one of the four core toolkit-evaluation strategies (Ledo et al., 2018) — but the items below are basic functional/stability self-checks (does telemetry exist, does a build run stably, can the model backend be swapped), not a formal technical-performance benchmark; that kind of empirical benchmarking, where it happens at all in this dissertation, is RQ3's 45-trial test, not this category. Real-time responsiveness specifically is also flagged in adjacent virtual-human toolkit literature as a hard requirement for believable embodied interaction ("A Toolkit for Creating Intelligent Virtual Humans in Extended Reality" notes that real-time performance with minimal latency is mandatory for embodied user interaction).
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C7.1 | Exposed performance/latency telemetry | Code/doc inspection: check whether the SDK surfaces any built-in timing/telemetry, independent of any other RQ's own measurements. | 2 = built-in telemetry available; 1 = timestamps loggable but not natively surfaced; 0 = fully opaque, external instrumentation only | Simpson et al., 2022 — a comparable WoZ study explicitly names "technical issues such as latency caused by engaging a TTS engine at runtime" as a real, documented problem, not a hypothetical one — grounding why this needs to be measurable rather than assumed away |
| C7.2 | Standalone Quest 3 performance (frame rate / stability) | Run any one condition build standalone on Quest 3 for 5 minutes; note dropped frames, crashes, or thermal throttling if observed. | 2 = stable, no observed issues; 1 = usable but occasional stutter/slowdown; 0 = unstable/unusable standalone | Zhang et al., 2025 and Bai et al., 2025 — both run comparable embodied-agent/WoZ studies on Meta Quest hardware, making standalone Quest 3 performance a directly relevant, precedented test |
| C7.3 | Local vs. cloud model swap (relevant for offline/private research settings) | Doc/code check: can the LLM/STT be swapped from a cloud service to a local model (e.g. Ollama/LLaMA) via config, without code rewrite. | 2 = swappable via config; 1 = swappable but requires code changes; 0 = cloud-only | General research-platform flexibility consideration — not tied to a specific paper, flagged honestly as researcher judgement |

## C8 — XR Compatibility (2 items)
 
**Why this category is here:** Meta Quest headsets are the hardware this line of research is actually run on — Bai et al.'s SEAM prototype uses a Meta Quest headset (via Quest Link) for its embodied playback experience, and Zhang et al.'s Wizard-of-Oz embodied-agent study runs specifically on a Meta Quest 3 (Bai et al., 2025; Zhang et al., 2025). Testing standalone XR performance on this hardware is therefore directly aligned with how comparable doppelgänger/embodied-agent studies are conducted.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C8.1 | Headset tracking integration (face/hand tracking feeding into agent perception) | Check whether user's own face/hand tracking data (if available on hardware) can feed into the agent's perception loop (per C4.2). | 2 = confirmed integration; 1 = documented but not tested; 0 = not supported | Li et al., 2026 — vision/perception input listed as core capability; tested here specifically in the XR-hardware context |

## Developer experience — not scored in RQ1

Developer accessibility (documentation clarity, setup effort, example
usefulness, debugging difficulty, extensibility) is evaluated separately in
RQ4, using a think-aloud usage study and a dev journal — this is Ledo et
al.'s "usage evaluation" strategy, distinct from the heuristic capability
checks C1–C8 perform. It is not scored as an RQ1 capability item: RQ1
establishes what the SDK provides; RQ4 establishes whether a real developer
can actually pick it up and use it.
