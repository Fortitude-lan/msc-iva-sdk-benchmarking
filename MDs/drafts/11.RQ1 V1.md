# RQ1 What doppelgänger-relevant capabilities does the SDK support, and where are its practical boundaries?


### What "practical boundaries" means — three layers, not one

| Boundary layer | What it asks | Evidence needed | Example |
|---|---|---|---|
| **Existence boundary** | Does the capability exist at all? | A single check/test is sufficient | C5.3 — can a constraint be injected into the system prompt |
| **Reliability boundary** | Does an existing capability hold up under repeated use? | Requires repeated trials, not a one-off test | C5.5 / C5.6 — how reliably a constraint is actually enforced (imported from RQ2 §3.2) |
| **Accessibility boundary** | Can a real researcher actually discover and use an existing, reliable capability? | Requires observing real people, not code inspection | C9 — documentation clarity, setup effort (imported from RQ3) |

## C1 — Avatar Representation (2 items)
 
**Why this category is here:** Embodied visual representation is listed as a defining capability of an IVA toolkit by its own authors (Li et al., 2026). For doppelgänger research specifically, the stand-in is explicitly defined as "an embodied virtual agent" representing the absentee (Bai et al., 2025) — so how flexibly that embodiment (appearance, voice) can be configured is not a cosmetic detail but core to whether attendees perceive the agent as an adequate stand-in.

## C2 — Speech / Verbal Behaviour (4 items)
 
**Why this category is here:** Speech is listed among the toolkit's core multimodal capabilities by its own authors (Li et al., 2026). More specifically for doppelgängers, the stand-in exists precisely to "generate reasonable responses in meetings and mimic the absentee's communication style" via an LLM-driven voice channel (Bai et al., 2025) — so verbal behaviour control isn't optional, it's the mechanism the whole doppelgänger concept runs on.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C2.1 | Manual/scripted speech trigger, independent of LLM loop | Call `agent.Speak(text)` directly from a test script (not through the LLM pipeline) with an arbitrary string. Confirm the agent speaks exactly that text. | 2 = works directly, arbitrary text; 1 = works but only with pre-registered/whitelisted strings; 0 = not callable outside LLM loop | Needed specifically for Condition A / WoZ-style doppelgänger studies (Bai et al., 2025 discusses SEAM's own reliance on scripted/controlled responses in Study 1) |
| C2.2 | Multilingual STT/TTS support | Check docs/code for language parameter on STT and TTS services. Run one non-English utterance through STT if feasible, or confirm via documentation + config field. | 2 = language selectable via config, confirmed working; 1 = documented but not verifiable without extra account setup; 0 = English-only | General research-platform generalisability — not tied to a specific paper; included because a platform limited to one language restricts which participant populations doppelgänger studies can recruit |
| C2.3 | Interrupt / barge-in mid-speech | While the agent is mid-`Speak()`, call `agent.Speak()` again or a stop/interrupt method. Observe whether the first utterance is cut off cleanly or causes an error/overlap. | 2 = clean interrupt via public method; 1 = interrupt possible but causes audio overlap/glitch; 0 = no interrupt path found | Li et al., 2026 — the SDK's own end-user pilot evaluation found "multiple participants reported difficulties interrupting the IVA during long responses," i.e. this is a documented real limitation, not a hypothetical concern |

## C3 — Non-verbal Behaviour (3 items)
 
**Why this category is here:** Gesture, facial expression, and gaze are explicitly listed among the toolkit's core multimodal capabilities (Li et al., 2026). More concretely, SEAM's own recording/replay mechanism depends on capturing "every movement (including gestures, facial expressions, locomotion...)" (Bai et al., 2025) — meaning non-verbal channels aren't decorative, they're part of what a stand-in must be able to reproduce for a doppelgänger experience to feel complete.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C3.1 | Manual/scripted gesture trigger | Call `agent.PerformAction(actionName)` directly for 3 different pre-built actions. Confirm each plays the correct animation on demand. | 2 = arbitrary registered action playable on demand; 1 = only reachable via LLM decision, not directly callable; 0 = not found | Li et al., 2026 — gesture control listed as core capability; needed for Condition A manual control |
| C3.2 | Manual/scripted facial expression trigger | Call `agent.ExpressEmotion(emotionName)` directly for 3 different expressions. Confirm each renders correctly. | 2 = directly callable; 1 = only LLM-selected; 0 = not found | Li et al., 2026 — facial expression control listed as core capability |
| C3.3 | Gesture/expression library breadth relevant to doppelgänger use (culturally-adaptive, persona-consistent options) | Count distinct actions/expressions available in the shipped library (Action Manager / Facial Expression Manager asset lists). ## C4 — Listening / Input (2 items)
 
**Why this category is here:** The toolkit's own paper lists STT and "vision-based multimodal prompting" as core input capabilities (Li et al., 2026). More specifically, SEAM's stand-in is explicitly described as being "configured with their responses to the agenda items" ahead of time (Bai et al., 2025) — i.e. a doppelgänger needs to be primed with context beyond whatever it can pick up live through a microphone, which directly motivates C4.1.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C4.1 | External context injection bypassing live STT (e.g. feeding meeting transcript text directly) | Check for a public method/field that accepts text input directly (not through microphone/STT). Attempt to feed a test string and confirm the agent responds to it as if it had "heard" it. | 2 = documented text-injection API; 1 = possible only by spoofing STT output internally; 0 = no path found | Bai et al., 2025 — stand-ins are pre-configured with the absentee's responses/context, not purely reliant on live listening |
| C4.2 | Multimodal/visual perception of the environment or other participants | Check for VLM/vision input hooks. Test whether the agent can react to a simple visual cue (e.g. an object or avatar appearance) if hardware allows, or confirm via code walkthrough if hardware testing isn't feasible in the time available. | 2 = confirmed working visual input path; 1 = documented/code-present but not independently verified; 0 = not present | Li et al., 2026 — vision-based multimodal prompting listed as a core toolkit capability |

## C5 — Control and Autonomy (5 items) — core category
 
**Why this category is here:** This is the category with the strongest, most direct literature grounding. SEAM's own ethics/trust discussion states the core tension this category operationalizes almost word-for-word: *"the extent to which stand-ins should respect absentee autonomy is unclear... without any control from the absentee, stand-ins may cause unexpected consequences"* and that *"providing transparent control systems is a crucial first step towards allowing absentees to trust their stand-in"* (Bai et al., 2025). C5 is essentially this literature-level statement turned into testable checklist items — and it's also the category that ties most directly into RQ2's autonomy-spectrum findings. On the WoZ-specific items (C5.1, C5.2), Simpson et al. (2022) and the Welicit paper add a second, methods-level layer of grounding: both are studies whose entire contribution is building custom WoZ tooling for virtual environments precisely because none exists natively — confirming that this SDK's gap here is a known, documented pattern in the field, not an isolated flaw.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C5.1 | Full manual control path exists (WoZ feasibility) | From RQ2 Condition A build: was a complete WoZ operator flow (speech + gesture + expression, all human-triggered) achievable using only public API calls? | 2 = fully achievable with public API only; 1 = achievable but required significant custom UI/glue code (~200 lines, per RQ2 §2.1); 0 = not achievable without SDK modification | Bai et al., 2025 — "transparent control systems" as the trust-building baseline. Also Simpson et al., 2022 — a comparable WoZ pilot study reports needing significant iteration on the operator interface itself, so the effort required here is an expected, documented feature of WoZ implementation, not a sign something went wrong |
| C5.2 | Native WoZ/operator interface shipped with SDK | Doc/code search for any built-in operator panel or manual-override UI. | 2 = shipped and usable as-is; 1 = partial scaffolding exists but incomplete; 0 = none — confirmed absent, must build from scratch | Simpson et al., 2022 and the Welicit paper — both are entirely about researchers having to build custom WoZ tooling because none existed for their VR/virtual-environment context; this SDK's lack of native WoZ tooling is consistent with a documented gap in the field, not a unique shortcoming |
| C5.3 | Persona/role constraint injection (system-prompt-level) | Confirm `additionalDescription` field (or equivalent) accepts free-text constraints and is passed into `BuildSystemPrompt()`. | 2 = confirmed field exists and is passed to system prompt; 1 = only settable by editing source; 0 = not present | Bai et al., 2025 — absentees need a way to bound what the stand-in can say/do without controlling every utterance individually |
| C5.4 | Enforcement mechanism beyond raw prompt-text injection | **Static code inspection, not an empirical trial.** Check `BuildSystemPrompt()` and the surrounding pipeline: once a constraint is injected, does the SDK do anything further to enforce it (validate output against the rule, reject/retry on violation, restrict output to a fixed schema/vocabulary), or does the constraint text get concatenated into the prompt with no additional engineering safeguard? | 2 = explicit enforcement/validation layer confirmed (e.g. output checked, auto-retry on violation); 1 = partial safeguard (e.g. gestures/emotions are constrained to a fixed vocabulary, but free-text speech is unchecked); 0 = confirmed no enforcement layer — compliance rests entirely on the underlying LLM's own instruction-following | Direct source-code finding: `AgentBase.BuildSystemPrompt()` only concatenates `additionalDescription` into the prompt string; no validation/retry layer exists. This is the static, architectural counterpart to C5.5/C5.6 below — it explains *why* those empirical reliability scores come out the way they do, not just *what* they are |
| C5.5 | Role constraint reliability (Condition B only) | **Imported directly from RQ2 §3.2 constraint violation rate test, Condition B (constrained AI) only.** Condition A is excluded because compliance is enforced by the human operator by construction; Condition C is excluded because it has no explicit machine-readable constraint to violate. | 2 = agent consistently respects constraints across all trials (no observed violations, or isolated single-trial deviation attributable to model variance); 1 = agent generally attempts compliance but exhibits recurring violations across multiple trials; 0 = agent systematically fails to respect constraints (violations occur in the majority of trials) | Bai et al., 2025 — directly tests the paper's stated concern about accountability: "are errors... attributed to the system... or do they reflect on the absentee?" |
| C5.6 | Decision-boundary enforcement (Condition B only) | **Imported directly from RQ2 §3.2**, same trial set as C5.5, filtered specifically for "refused to commit" vs "committed anyway." Same exclusion logic as C5.5. | Same categorical scale as C5.5, applied to the decision-specific subset of trials | Same as C5.5 — this is the specific failure mode (unauthorized commitments) that most threatens absentee trust per Bai et al., 2025 |
 
---

¹ **Note on C5.4/C5.5 scoring method:** Rather than scoring against an arbitrary numeric threshold, C5.4 and C5.5 are scored from the RQ2 §3.2 trial matrix (3–5 differently worded elicitation prompts × 2–3 repetitions each). A violation isolated to a single trial with no repetition under the same prompt variant is treated as model-sampling noise and does not lower the score. A score of 1 requires a *reproducible* pattern — i.e. violations that recur under a specific prompt variant, or that are distributed non-trivially across multiple variants — rather than a single one-off deviation. This avoids relying on a numeric cutoff that cannot be principled (e.g. why 10% and not 15%), while still distinguishing genuine constraint-enforcement gaps from incidental model variance.

## C6 — Reproducibility / Logging (3 items)
 
**Why this category is here:** This is the second most directly-grounded category. SEAM's entire second-iteration mechanic depends on recording "every movement... voice and every object's changes in 3D space" so the absentee can later replay and review what their stand-in did (Bai et al., 2025) — this is a concrete, literature-stated functional requirement of doppelgänger systems, not just general good research practice.
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C6.1 | Interaction logging (conversation history, actions taken) exposed programmatically | Code/doc search for a logging hook or accessible history object. Attempt to read back a log of the last N turns. | 2 = structured log accessible via public API; 1 = raw data exists but requires manual extraction/parsing; 0 = not exposed | Bai et al., 2025 — absentees need to be able to review "what the stand-in responded to during the meeting" |
| C6.2 | Deterministic replay of a given input (same input → same output, non-LLM-dependent factors only) | For Condition A only (deterministic by design), confirm repeated identical button presses always produce identical output. | 2 = fully deterministic (verified via 5 repeat trials); 1 = mostly deterministic with rare deviation; 0 = non-deterministic even under manual control | Ledo et al., 2018 — general scientific-reproducibility expectation for a research platform, not doppelgänger-specific |
| C6.3 | Session/interaction recording (video/audio/state capture) | Doc/code search for a built-in session recorder. | 2 = built-in recorder available; 1 = requires external tool (e.g. screen recording) with no SDK-level state capture; 0 = no support, not even partial | Bai et al., 2025 — session recording is the literal mechanism SEAM's asynchronous replay is built on |

## C7 — Technical Performance (3 items)
 
**Why this category is here:** Reporting technical performance evidence is one of Ledo et al.'s four core toolkit-evaluation strategies, used here to ground methodological rigour (Ledo et al., 2018). Real-time responsiveness specifically is also flagged in adjacent virtual-human toolkit literature as a hard requirement for believable embodied interaction ("A Toolkit for Creating Intelligent Virtual Humans in Extended Reality" notes that real-time performance with minimal latency is mandatory for embodied user interaction).
 
| ID | Item | Test procedure | Scoring | Why this item (source) |
|---|---|---|---|---|
| C7.1 | Exposed performance/latency telemetry | Check whether the SDK surfaces any built-in timing/telemetry (vs. requiring manual instrumentation, as done in RQ2 §5). | 2 = built-in telemetry available; 1 = timestamps loggable but not natively surfaced; 0 = fully opaque, external instrumentation only | Simpson et al., 2022 — a comparable WoZ study explicitly names "technical issues such as latency caused by engaging a TTS engine at runtime" as a real, documented problem, not a hypothetical one — grounding why this needs to be measurable rather than assumed away |
| C7.2 | Standalone Quest 3 performance (frame rate / stability) | Run any one condition build standalone on Quest 3 for 5 minutes; note dropped frames, crashes, or thermal throttling if observed. | 2 = stable, no observed issues; 1 = usable but occasional stutter/slowdown; 0 = unstable/unusable standalone | Zhang et al., 2025 and Bai et al., 2025 — both run comparable embodied-agent/WoZ studies on Meta Quest hardware, making standalone Quest 3 performance a directly relevant, precedented test |
| C7.3 | Local vs. cloud model swap (relevant for offline/private research settings) | Doc/code check: can the LLM/STT be swapped from a cloud service to a local model (e.g. Ollama/LLaMA) via config, without code rewrite. | 2 = swappable via config; 1 = swappable but requires code changes; 0 = cloud-only | General research-platform flexibility consideration — not tied to a specific paper, flagged honestly as researcher judgement |

## C8 — XR Compatibility (2 items)
 
**Why this category is here:** Meta Quest headsets are the hardware this line of research is actually run on — Bai et al.'s SEAM prototype uses a Meta Quest headset (via Quest Link) for its embodied playback experience, and Zhang et al.'s Wizard-of-Oz embodied-agent study runs specifically on a Meta Quest 3 (Bai et al., 2025; Zhang et al., 2025). Testing standalone XR performance on this hardware is therefore directly aligned with how comparable doppelgänger/embodied-agent studies are conducted.

## C9 — Developer Experience (5 items) — fully delegated to RQ3
 
**Why this category is here:** Unlike C1–C6, this category isn't grounded in doppelgänger-specific literature — it's grounded in general HCI toolkit evaluation methodology. Ledo et al. identify "usage evaluation" as one of the four core strategies for toolkit research precisely because a toolkit's domain-fit (RQ1's other categories) doesn't guarantee anyone can actually adopt it (Ledo et al., 2018). C9 supplies that adoption-feasibility evidence, independent of whether the SDK is theoretically capable.
