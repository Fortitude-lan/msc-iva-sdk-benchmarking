# RQ2 How does the SDK support the two extremes of control in doppelgänger research: fully human-controlled and fully AI-driven scenarios?

**Outcome/contribution** (written as prose around this table, not derived
from it as a formula):
- What researchers gain and give up at each control extreme
- Which kinds of doppelgänger research each extreme is suitable for
---

**How this feeds RQ0:** Doppelgänger research is not one paradigm. Psychology-style studies may require full scripted control over what the agent says and does. Exploratory HCI studies want to see what an AI-driven doppelgänger does when given only a role and
some context, without every line being pre-authored. RQ2 asks whether the same SDK can support **both ends** of this spectrum — and if so, what it costs the researcher to get there.
 
*Note: A SDK that only serves one end is only "suitable" for a narrow slice of doppelgänger research. RQ2 documents what each one `costs` and `buys` the researcher, so a future doppelgänger researcher can pick the right mode for their paradigm with eyes open.*



## 1. Why this is not a single, symmetric evaluation
 
The two extremes are not two levels of one variable measured with the same
instrument. They are two structurally different mechanisms:
 
- **Human-controlled** — nothing is built or run. The evidence is literature
  on Wizard-of-Oz (Welicit; Zhang et al.'s CHI'25 embodied-agent WOz study;
  the desert-environment WOz pilot) plus a re-use of SDK capability facts
  already established in RQ1 (whether manual speech/gesture/expression
  triggers exist, whether a native operator UI exists). Per Ledo et al.'s
  own definition, a demonstration requires *building something that proves
  existence* — since nothing is built here, this is **not** a demonstration.
  It is a literature-grounded analysis.
- **AI-driven** — something is actually built and run: a small, concrete
  doppelgänger scenario using the SDK's native `GeminiLiveAgent` pipeline,
  unmodified. This **is** a demonstration in Ledo et al.'s sense — an
  existence proof that the SDK can produce this class of behaviour.
Because the two sides use different evidence types, RQ2 does not produce one
shared metrics table scored identically on both ends. Section 3 is where the
two separate bodies of evidence are brought together as an interpretive
argument, not as a repeated-measures comparison.
 
This follows the same logic Bai et al.'s SEAM used to justify not running a
controlled A/B comparison for their stand-in study — isolating variables
into a symmetric trial "would have constrained the space of inquiry" at this
exploratory stage. It is also a direct continuation of a gap SEAM names
explicitly: their own stand-in was Wizard-of-Oz controlled, and their future
work calls for testing an **AI-powered** stand-in. RQ2's AI-driven extreme
is where this dissertation picks that up.

## 2. Human-controlled extreme
 
**Not implemented. No experiment is run.** This is a deliberate scope
decision: answering whether the SDK supports the human-controlled end does
not require building a full Wizard-of-Oz operator system from scratch — it
requires knowing what WoZ as a paradigm generally offers/costs (from
literature) and what the SDK itself already exposes toward that end (from
RQ1). Welicit (Bellucci et al.) and Simpson et al.'s "A Wizard or a Fool?"
both show that WoZ tooling is not a solved problem — building one well is
itself non-trivial engineering work — which is part of why this dissertation
does not attempt to build one as a side effort to RQ2.
 
### Method / evidence
- Wizard-of-Oz literature (Welicit; Zhang et al. CHI'25; desert-environment
  WOz pilot) — establishes what this control paradigm generally offers and
  costs a researcher
- Re-use of RQ1 capability-inspection findings: whether the SDK exposes
  manual triggers for speech / gesture / expression (`agent.Speak()`,
  `agent.PerformAction()`, `agent.ExpressEmotion()`), and whether a native
  operator/WOz interface exists
### Output
 
| Question | Evidence source |
|---|---|
| Can behaviour be manually triggered? | RQ1 manual speech/gesture/expression checks |
| Native operator interface? | RQ1 documentation/code inspection |
| Extra tooling required? | Derived from the above + WoZ literature |
| Who decides behaviour? | Human operator, by definition of this mode |
| Main benefit / main cost | Interpreted from SDK findings + WoZ literature |
| Best suited to | Interpreted from SDK findings + WoZ literature |
 
This table is filled in once the corresponding RQ1 findings are final — the
protocol defines what to check, not the answer in advance. No trial data,
no timing measurements are collected for this extreme.

## 3. AI-driven extreme
 
**Actually built and run.** One small, concrete scenario, following directly
from the doppelgänger/stand-in paradigm established in SEAM.
 
### Scenario
A colleague who cannot attend today's project meeting is represented by a
doppelgänger stand-in, which fields questions from the other attendees.
 
**Configuration:**
- Identity and role (who she is, what she is responsible for on the project)
- A small set of background facts (current project status)
- No additional constraint rules — this stays a plain persona/context
  configuration, not a hard-rule test. Hard-rule constraint testing belongs
  to RQ3, not here.
**What runs the interaction:** the SDK's existing `GeminiLiveAgent` pipeline
is used without modifying the SDK core. Only the stand-in's identity, role,
and background context are configured for the scenario. The finding here is
not "zero setup" — it is that no custom control tooling or SDK modification
is required to get an autonomous, embodied doppelgänger running; the SDK's
own combination of system prompt, LLM/VLM reasoning, speech, gesture and
facial expression already constitutes a working autonomous pipeline, and
this demonstration tests whether that existing workflow can be repurposed
for the doppelgänger stand-in use case.
 
**Representative questions asked (not a repeated trial protocol — walked
through once as a demonstration):**
1. Who are you, and why are you here?
2. Can you give a quick update on the project?
3. What are you currently working on?
4. What do you think the next step should be?
5. Is there anything you'd like the team to know?
### What gets recorded
- Which SDK components were used (speech, gesture, expression, LLM pipeline)
- Whether it ran without issues
- What, if anything, needed extra configuration
- Limitations to observe (not assumed in advance) — for example, whether
  answers drift off-topic, whether identity details stay consistent between
  answers, or whether response delay is noticeable
This is a descriptive, existence-proof account — not a scored or repeated
experiment, and not a latency evaluation. A full timing benchmark is not
collected for this extreme.

## 4. Cross-endpoint synthesis
 
Not a leaderboard, not a repeated-measures comparison. This is where the two
separate bodies of evidence (§2, §3) are read side by side to answer what
RQ2 actually asks: what does each extreme cost, and what does it buy.
 
| Aspect | Human-controlled | Fully AI-driven |
|---|---|---|
| Who decides behaviour? | Researcher/operator | AI, at runtime |
| SDK support | Manual behaviour primitives only | Native, ready-to-use AI pipeline |
| Extra requirements | External operator UI/tooling | Persona/context configuration |
| Runtime researcher involvement | High, continuous | Low, after initial setup |
| Behavioural flexibility | Limited to prepared content | Open-ended |
| Direct behavioural control | High | Reduced |
| Likely / supported research use | Highly scripted / tightly controlled studies | Open-ended / exploratory studies |
